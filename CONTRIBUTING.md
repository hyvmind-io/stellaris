# Contributing to Stellaris

Thank you for your interest in contributing to Stellaris! This guide will help you get set up and familiar with the project's development workflow.

## Getting Started

### 1. Fork and clone

```bash
git clone https://github.com/<your-username>/stellaris.git
cd stellaris
```

### 2. Install dependencies

Stellaris uses [pnpm](https://pnpm.io/) as its package manager:

```bash
pnpm install
```

### 3. Set up the local database

The project uses Cloudflare D1 (SQLite) for metadata storage. For local development, Wrangler emulates D1 automatically. Run the setup script to apply migrations:

```bash
pnpm db:setup
```

This uses `wrangler d1 migrations apply --local` to apply only pending migrations (tracked in a `D1_MIGRATIONS` ledger table inside the local DB). It is safe to re-run — already-applied migrations are skipped automatically. After setup, create an API key:

```bash
pnpm db:create-key --name "local-admin" --permissions '["admin"]'
```

### 4. Configure environment

Copy the example environment file for local development:

```bash
cp .env.example .env
```

This sets `STORAGE_BACKEND=local` so uploads go to `.storage/` on disk instead of R2. All other env vars have sensible defaults via Zod validation.

If you need secret overrides (S3 credentials, custom auth secret, etc.), create `.env.local` — it takes precedence over `.env`:

```bash
cp .env.example .env.local
# Edit .env.local with your secret values
```

Both `.env` and `.env.local` are gitignored. See `.env.example` for all available options.

### 5. Start the dev server

```bash
pnpm dev
```

This starts the Next.js development server with Turbopack at [http://localhost:3000](http://localhost:3000). Cloudflare bindings (D1, R2) are emulated locally via `@opennextjs/cloudflare`.

## Development Workflow

### Running tests

```bash
# Run all tests
pnpm test

# Run tests in watch mode (default Vitest behavior)
pnpm test

# Run with Vitest UI (browser-based test viewer)
pnpm test:ui

# Run with coverage report
pnpm test:coverage
```

Tests use [Vitest](https://vitest.dev/) with [happy-dom](https://github.com/nicedoc/happy-dom) for DOM emulation. Test files live in the `__tests__/` directory, mirroring the source structure.

### Type checking

```bash
pnpm type-check
```

The project uses TypeScript in strict mode. All code must pass type checking before merging.

### Linting

```bash
pnpm lint
```

Linting is configured via ESLint with the `eslint-config-next` preset.

### Database changes

If you modify the schema in `db/schema.ts`:

```bash
# Generate a new SQL migration from the schema diff
pnpm db:generate

# Apply pending migrations locally (idempotent — safe to re-run)
pnpm db:setup

# Browse the database visually
pnpm db:studio
```

Migrations are generated by [Drizzle Kit](https://orm.drizzle.team/kit-docs/overview) into the `drizzle/` directory. Migrations are applied via `pnpm db:setup` (local) or `pnpm db:setup:remote` (remote), which use `wrangler d1 migrations apply` under the hood — `drizzle-kit migrate` and `drizzle-kit push` don't work with D1 directly.

### Resetting the database

If you need a clean slate for local development:

```bash
# Wipe local database (removes .wrangler/ state)
pnpm db:reset

# Re-apply migrations after reset
pnpm db:setup
```

`db:reset` only deletes the local database files. `db:setup` only applies migrations. For a full reset, run both commands in sequence.

For remote database operations (use with caution):

```bash
# Apply migrations to remote D1
pnpm db:setup:remote

# Drop all remote tables (DESTRUCTIVE — requires confirmation)
pnpm db:reset:remote

# After remote reset, re-apply migrations:
pnpm db:setup:remote
```

### Preview with Cloudflare Workers

To test the full Cloudflare Workers build locally:

```bash
pnpm preview
```

This builds the application with the OpenNext.js Cloudflare adapter and runs it in the Wrangler local runtime.

## Code Style

- **TypeScript** — Strict mode is enabled. Use explicit types for function signatures and public APIs.
- **Zod** — All API input is validated with Zod schemas defined in `lib/validation/registry.ts`.
- **Drizzle ORM** — Database queries go through the data layer in `lib/data/`. Don't use raw SQL in route handlers.
- **Error responses** — Use the helpers in `lib/api/errors.ts` (`notFound()`, `badRequest()`, `conflict()`, etc.) for consistent error formatting.
- **Response helpers** — Use `lib/api/response.ts` (`jsonResponse()`, `binaryResponse()`, etc.) for API responses.
- **Path aliases** — Use `@/` for imports from the project root (e.g., `import { getDb } from "@/db/client"`).

## Project Structure

```
app/v1/          → API route handlers (Terraform protocol + extended API)
db/              → Drizzle schema and D1 client
lib/api/         → Response/error helpers
lib/auth/        → API key management and auth middleware
lib/data/        → Data access layer (modules, providers, stats)
lib/storage/     → R2 storage operations
lib/validation/  → Zod schemas for request validation
components/      → React UI components (shadcn/ui + custom)
__tests__/       → Test suites
scripts/         → Database setup/reset scripts
```

## Pull Request Process

1. **Create a feature branch** from `main`:

   ```bash
   git checkout -b feature/my-feature
   ```

2. **Make your changes** following the code style guidelines above.

3. **Add or update tests** for any new functionality.

4. **Run the full check suite** before submitting:

   ```bash
   pnpm type-check && pnpm lint && pnpm test
   ```

5. **Open a pull request** against `main` with a clear description of:
   - What the change does
   - Why it's needed
   - Any breaking changes or migration steps

6. **Address review feedback** — all PRs require review before merging.

## Reporting Issues

If you find a bug or have a feature request, please open an issue with:

- A clear title and description
- Steps to reproduce (for bugs)
- Expected vs actual behavior
- Your environment (Node.js version, OS, etc.)
